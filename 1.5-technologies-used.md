# 1.5. Technologies Used

The ScentStation system is built on a three-tier architecture: the presentation tier (frontend), the business logic tier (backend) and the device tier (perfume sampling machines). These tiers communicate through two protocols: REST API between the frontend and the backend, and MQTT between the backend and the devices.

## 1.5.1. Backend Technologies

| Technology | Version | Role |
|---|---|---|
| Java (Temurin JDK) | 21 LTS | Primary programming language |
| Spring Boot | 3.3.5 | Application framework and REST API |
| Spring Security | 6.x | Authentication and authorization |
| Spring Data JPA / Hibernate | 6.x | Object-relational mapping and data access |
| Maven | 3.9+ | Dependency management and build tool |

Java and Spring Boot were selected as they are mandatory requirements of the course. Spring Boot also provides built-in dependency injection, transaction management and security mechanisms, allowing the team to focus on business logic rather than building infrastructure from scratch. JDK 21 is a long-term support release, stable and fully compatible with Spring Boot 3.

## 1.5.2. Database

| Technology | Version | Role |
|---|---|---|
| PostgreSQL | 16 | Relational database management system |
| Flyway | 10.x | Database schema version control |

PostgreSQL was chosen for its strong support of partial unique indexes — the mechanism the system relies on to guarantee that each order has only one active dispense command and each slot holds only one active bottle. Flyway allows all five team members to modify the database schema without conflicts, since every change is recorded as a sequentially numbered migration script.

## 1.5.3. Device Communication

| Technology | Version | Role |
|---|---|---|
| MQTT | 3.1.1 | Messaging protocol for IoT devices |
| Eclipse Mosquitto | 2.0 | MQTT broker |
| Eclipse Paho | 1.2.5 | MQTT client library for Java |

MQTT is a lightweight publish/subscribe protocol well suited to resource-constrained devices and unreliable network conditions. Since the project does not involve purchasing hardware, the team developed a Java simulator that acts as a real machine: it receives dispense commands, simulates the dispensing delay, returns the result and periodically publishes telemetry data. The entire MQTT flow is genuine; only the physical device is simulated.

## 1.5.5. Security

| Technique | Purpose |
|---|---|
| JWT (JSON Web Token) | Stateless user authentication |
| BCrypt | One-way password hashing |
| RBAC (Role-Based Access Control) | Role-based authorization |
| HMAC-SHA256 | Signing dispense commands to prevent forgery |

As the platform serves multiple brands simultaneously, data belonging to different brands must be isolated from one another. The team uses Hibernate's `@Filter` mechanism combined with a `TenantContext` to automatically filter records according to the brand of the currently authenticated user.

## 1.5.6. Development Tools

| Tool | Role |
|---|---|
| IntelliJ IDEA | Integrated development environment for backend work |
| Visual Studio Code | Integrated development environment for frontend work |
| Git and GitHub | Source control and code review through Pull Requests |
| GitHub Actions | Continuous integration, automated build and test |
| Jira | Task management following the Scrum framework |
| Docker and Docker Compose | Containerisation and consistent development environment |
| Swagger / OpenAPI | API documentation, enabling parallel development |
| Postman | Manual API testing |
| JUnit 5 and Mockito | Unit testing |

Docker Compose plays a key role in giving all five members an identical runtime environment: a single command brings up PostgreSQL and Mosquitto, avoiding the familiar "it works on my machine" problem. Agreeing on the OpenAPI specification early also allows the frontend work to proceed in parallel with the backend through mocked responses, rather than waiting for the APIs to be completed.
