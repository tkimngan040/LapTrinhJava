# Chapter 4. Conclusion

## 4.1. Achievements

The project set out to build a working prototype of a multi-brand perfume
sampling platform, not a demonstration of screens. Measured against Chapter 1,
the three tiers designed in Chapter 2 exist and talk to one another: a Spring
Boot backend of 149 Java source files and 77 REST endpoints, a PostgreSQL
schema of ten Flyway migrations running under `ddl-auto: validate`, an MQTT
gateway, and a device simulator that speaks the same signed protocol a real
kiosk would.

Four results are worth naming, because each one was a design decision before it
was code.

**The order lifecycle is a state machine, not a status column.**
`OrderStateMachine` admits only the transitions of Section 2.6, rejects
everything else with an exception rather than a silent write, and refuses to
resolve an `UNCERTAIN` order automatically: BR14 says a human must decide, and
the code enforces that rather than documenting it. Thirteen unit tests hold the
boundary.

**A dispensing command cannot be forged or replayed.** Every command carries an
HMAC-SHA256 signature over canonical JSON, an idempotency key and an expiry, and
a partial unique index allows one active command per order, so a duplicated
device result deducts stock exactly once. The property is tested from both
sides: `CommandSignerTest` on the signature, `DispenseServiceTest` on the single
deduction.

**Device misbehaviour is a tested path, not an afterthought.** The simulator
takes `--fault=reject|interlock|silent|duplicate|offline`, which let the team
run the exception paths of Section 2.9.4 on purpose rather than waiting for them
to appear during a demonstration. Watchdogs for command acknowledgement, result
timeout and heartbeat put the system into a defined state when a device goes
quiet, and `DiagnosticInterlockTest` holds the rule that a diagnostic spray
never bypasses a door, error or empty-slot condition.

**Observability is written into the schema rather than added on top.** Alerts
are raised from the three places the system can learn that something is wrong —
a failed dispense, a machine condition reported over MQTT, and a bottle falling
below its threshold — are deduplicated by an incident key, and escalate into a
maintenance ticket when critical. Audit records are append-only because a
migration makes them so, not because the code remembers to be careful.

Beyond the system itself, five people changed one repository for eight weeks
without losing work: ownership is written down in `OWNERS.md`, every change
reached `main` through a pull request another member reviewed, and the schema
moved only through numbered migrations. Section 4.4 records what that cost and
where it failed.

## 4.2. Limitations

These limitations follow the implementation assessment in [Section 3.3](<03.Implementation and Testing.md#334-not-yet-implemented>).

| Area | Limitation and practical effect |
| :--- | :--- |
| **Access and catalogue — FR1–FR2** | Sign-in and role/tenant restrictions cover the implemented APIs. Brand and user administration lacks a server-side workflow. Per-user location and machine grants, complete configuration history and promotional pricing remain open. |
| **Payments, dispensing and recovery — FR3–FR4** | The payment and refund providers are simulated. Live provider integration and reconciliation remain open. IT-09 recorded a failure in duplicate signed webhook handling. IT-02 and IT-04 observed the expected order status and found no durable incident. IT-03 stopped at the machine status assertion, before checking the alert. The operator review queue reads order states, which leaves incident persistence outstanding. [Recorded test results](../docs/test-plan.md#implementation-and-execution-status) |
| **IoT and inventory — FR4–FR6** | Development MQTT uses plain TCP. The simulator checks signatures and simulated safety conditions. Production device identity, revocation, persistent telemetry and reconnect buffering remain open. Confirmed sale deduction is implemented. Server-side inventory intake/refill/adjustment, diagnostic consumption, low-stock alert generation, and measured sensor reconciliation remain open. Hardware safety and dosage accuracy require physical tests. |
| **Alerts and maintenance — FR7–FR8** | Browser screens demonstrate the interactions. The backend still needs alert persistence and delivery, escalation, linked ticket creation and the maintenance workflow with diagnostic closure checks. |
| **Reporting and audit — FR9–FR10** | The dashboard and CSV export use browser-side data. Database-backed tenant reports, historical metrics, broad audit coverage, server-side audit search and complete incident-linked transaction tracing remain open. Database audit records currently cover review and refund operations. |
